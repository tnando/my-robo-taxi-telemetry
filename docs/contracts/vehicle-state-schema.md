# Vehicle State Schema Contract

**Status:** Draft -- v1
**Target artifact:** JSON Schema (draft-2020-12)
**Owner:** `sdk-architect` agent
**Schema file:** [`schemas/vehicle-state.schema.json`](schemas/vehicle-state.schema.json)
**Last updated:** 2026-07-25

## Purpose

Canonical shape of vehicle state as consumed by the SDKs and rendered by consumer UIs. Defines every field name, type, unit, nullability rule, and -- critically -- which fields belong to which **atomic group**. Both the WebSocket protocol and the REST snapshot endpoint return subsets of this schema. Both SDKs generate types from it.

## Anchored requirements

- **FR-1.1, FR-1.2** -- telemetry field set (position, speed, heading, gear, battery, charge state, range)
- **FR-2.1** -- nav field set (destinationName, ETA, polyline, origin, etc.)
- **FR-4.2** -- vehicle-scoped API signatures (all SDK calls use `vehicleId`, not VIN)
- **NFR-3.1** -- atomic groups declared here: `navigation`, `charge`, `gps`, `gear`
- **NFR-3.3, NFR-3.4** -- self-consistency rules (partial groups are invalid)
- **NFR-3.5** -- every UI-rendered field is persisted and returned in the snapshot

---

## 1. Root `VehicleState` schema

The `VehicleState` object represents the complete current state of a single vehicle as persisted in the `Vehicle` table and delivered to SDK consumers. The canonical JSON Schema is at [`schemas/vehicle-state.schema.json`](schemas/vehicle-state.schema.json) (draft-2020-12).

### 1.1 Field reference

Every field below corresponds to a column in the `Vehicle` table or a value derived at broadcast time. Fields are grouped by category. The **Group** column indicates atomic group membership (fields without a group are delivered individually).

#### Cabin control fields (no atomic group — MYR-252)

Owner cabin-control **read-back** fields added by [MYR-252](https://linear.app/myrobotaxi/issue/MYR-252). All are optional (nullable, NOT in the schema `required` array) and delivered **individually on the live WebSocket `vehicle_update` stream** so the app can reconcile control UI against the car's real state instead of only command-ack optimism (MYR-251). They are gated by the `owner` mask allow-list (`internal/mask/tables.go` `vehicleStateOwnerFields`, rest-api.md §5.2.1). **Delivery caveat (updated by [MYR-269](https://linear.app/myrobotaxi/issue/MYR-269)).** The **five owner-control read-backs** the app renders as Lock / Trunk / Frunk / Climate / Charge-port — `locked`, `frunkOpen`, `trunkOpen`, `isClimateOn`, `chargePortDoorOpen` — are now **persisted server-side and returned on the DB-backed REST `/snapshot`** (NFR-3.5), so a non-streaming car surfaces the last-known value with no live socket. MYR-269 does this without the cross-repo Prisma migration MYR-253 anticipated: a Go-owned side table `go_vehicle_control_state` (keyed by vehicle id, no Prisma FK per CG-DL-9) is written on both the live persist path and the MYR-260 `/vehicle_data` backfill, and LEFT-joined into `VehicleRepo.GetByID`. **Extended by [MYR-273](https://linear.app/myrobotaxi/issue/MYR-273):** the cabin **SETTING levels** the owner sheet renders as numbers — `driverTempSetting`, `passengerTempSetting`, `fanSpeed`, `seatHeaterLeft`/`seatHeaterRight`, `seatHeaterRearLeft`/`seatHeaterRearCenter`/`seatHeaterRearRight`, `seatCoolerLeft`/`seatCoolerRight`, and `mediaVolume` — are now **persisted to the same `go_vehicle_control_state` side table** (migration 0010 adds the eleven nullable columns; same live-persist + `/vehicle_data` backfill write path, same per-field COALESCE last-writer-wins, same `VehicleRepo.GetByID` LEFT JOIN) and returned on `/snapshot`, so on sheet-open for a non-streaming car they surface the last-known value instead of a perpetual "—". This completes the MYR-253 hydration for the user-rendered cabin settings. **Extended by [MYR-274](https://linear.app/myrobotaxi/issue/MYR-274):** the two climate-**MODE** read-backs that back the owner Auto/Cool/Heat segment — `hvacAutoMode` (persisted as a nullable `TEXT` column holding the enum's string form) and `hvacAcEnabled` (nullable `BOOLEAN`) — are now **persisted to the same `go_vehicle_control_state` side table** (migration 0012; same live-persist + `/vehicle_data` backfill write path, same per-field COALESCE last-writer-wins, same `VehicleRepo.GetByID` LEFT JOIN) and returned on `/snapshot`, so a non-streaming car reflects its real Auto/Cool/Heat mode on a cold snapshot instead of an unresolved segment. Honest-unknown is preserved: a streamed `hvacAutoMode` of "Unknown"/empty is OMITTED (persists NULL, never overwrites a known mode), mirroring how an "Unknown" `hvacPower` omits `isClimateOn`. **Completed by [MYR-298](https://linear.app/myrobotaxi/issue/MYR-298):** the last two contracted read-backs — `seatVentEnabled` (nullable `BOOLEAN`) and `mediaPlaybackStatus` (nullable `TEXT` holding the enum's string form) — are now **persisted to the same `go_vehicle_control_state` side table** (migration 0014; same live-persist write path, same per-field COALESCE last-writer-wins, same `VehicleRepo.GetByID` LEFT JOIN) and returned on `/snapshot`. These two were neither persisted nor emitted anywhere but the live socket, so a client that missed the `vehicle_update` frame — a backgrounded phone, a sleeping car, any drop — could **never** learn them. Honest-unknown is preserved exactly as for `hvacAutoMode`: a streamed `mediaPlaybackStatus` of "Unknown"/empty is OMITTED (persists NULL, never overwrites a known status), so the stored value is only ever `Stopped`/`Playing`/`Paused`; `seatVentEnabled` is a plain bool where a real `false` overwrites. Unlike the MYR-269/279 columns these two are **stream-fed only** — Tesla's cached `/vehicle_data` climate subset carries neither, so the MYR-260 backfill never writes them. The **only** MYR-252 field that now stays WS-live-only is `hvacPower`, whose server-derived `isClimateOn` boolean IS persisted; a `/snapshot` omitting it is contract-valid (the schema documents WS/REST-snapshot as subsets, and all 21 are optional). Classification is **P0** — cabin comfort/lock/door/media state is not identifying, consistent with `speed`/`chargeLevel`/`gearPosition` (contrast: P2 is the platform's most-sensitive tier, reserved for payment/health per data-classification.md §0).

**REST-sourced population for non-streaming vehicles ([MYR-260](https://linear.app/myrobotaxi/issue/MYR-260)).** These fields are stream-fed, so a vehicle that is **not streaming** (in service, asleep, or offline) leaves them absent and the app renders a perpetual "— Syncing" (a client found his trunk physically open while the app said "Syncing"). To close that gap, the [`ServiceStatusMonitor`](../../internal/telemetry/service_status_monitor.go) — on the same debounced connectivity-edge read that resolves `in_service` (§2.4) — issues **one** additional unsigned authenticated `GET /api/1/vehicles/{vin}/vehicle_data` read **when the edge read shows the car is not streaming** (`in_service:true`, or Tesla connectivity `state != "online"`). The relevant sub-objects (`vehicle_state.locked` / `ft` / `rt` / `odometer`, `climate_state.is_climate_on` / `inside_temp` / `outside_temp`, `charge_state.charging_state` / `charge_port_door_open` / `battery_level`) are mapped onto the **same internal field names the stream decoder emits** and republished as a synthetic `VehicleTelemetryEvent`, so they flow through the identical broadcast + persist path and land on the wire as `locked`, `frunkOpen`/`trunkOpen` (folded back through the DoorState bitmask), `hvacPower`/`isClimateOn`, `interiorTemp`/`exteriorTemp` (Celsius→Fahrenheit), `chargeState`, `chargePortDoorOpen`, `odometerMiles`, and `chargeLevel`. The frame carries `lastUpdated` = the REST read time, which the app uses to render "last synced X ago". This is a **single, non-waking** read: if Tesla returns `408`/asleep/offline the read is a non-fatal skip (no retry-wake, no spam — it shares the §2.4 ~45s per-VIN debounce), leaving the last-known value so the SDK can show an honest "unavailable" rather than a spinner. GPS in the `vehicle_data` payload (P1) is never read or logged. No schema/field additions — this is a new **population path** for existing fields. **([MYR-269](https://linear.app/myrobotaxi/issue/MYR-269)) durability:** the four owner controls in this backfill (`locked`, `frunkOpen`/`trunkOpen`, `isClimateOn`, `chargePortDoorOpen`) previously flowed only through the live broadcast and evaporated the moment the socket dropped; they are now also persisted to `go_vehicle_control_state`, so the snapshot returns them even when no socket is held — which is the whole point of the non-waking backfill for an in-service car. **([MYR-300](https://linear.app/myrobotaxi/issue/MYR-300)) freshness gate:** this backfill writes NOTHING stream-sourceable while a live frame for that VIN has arrived within the last **120s** — Tesla's lagging connectivity flag makes the backfill fire for streaming cars too, and its possibly-cached values would otherwise overwrite fresher streamed state through the COALESCE upsert. REST-only `trim` still flows; a genuinely non-streaming car is unaffected. See the MYR-300 note under §2.4.

> **Ventilated-seat capability rule ([MYR-299](https://linear.app/myrobotaxi/issue/MYR-299); superseded-when-present by [MYR-308](https://linear.app/myrobotaxi/issue/MYR-308)).** **MYR-308 update:** a first-class capability field now exists — `seatCoolingCapable`, read from REST `vehicle_config.has_seat_cooling`. **Precedence:** when `seatCoolingCapable` is non-null it is AUTHORITATIVE and OUTRANKS the presence heuristic below — `false` means clients MUST NOT offer seat-cooling controls at all. The heuristic remains the required fallback while `seatCoolingCapable` is `null` (server predates MYR-308, or no vehicle-config read has completed for this car), so everything below still applies in that case. The original MYR-299 reasoning: `seatVentEnabled` is a **runtime on/off**, not a capability. The contracted stand-in is the **presence** of `seatCoolerLeft`/`seatCoolerRight`: a car without ventilated seats never emits Tesla protos **237/238** at all, while a car with them emits a value that **includes `0`** (present-but-off). Consumers therefore derive the capability as `seatCoolerLeft != null || seatCoolerRight != null`, and MUST NOT read the level's *value* as the signal.
>
> Two invariants make that inference sound, and both are load-bearing:
>
> 1. **Absence is meaningful only if presence is continuously re-asserted.** Tesla emits 237/238 on change only, so both fields carry `ResendIntervalSeconds: 120` in `DefaultFieldConfig` (matching the sibling comfort fields and the MYR-300 `defaultStreamFreshness` window). Without the resend, a vented car that has not touched its seat coolers since the last (re)connect is indistinguishable from a car that has none. **Propagation:** a `DefaultFieldConfig` change reaches a car only on a **re-push** — `POST /api/fleet-config/{vin}`, `ops fleet-config push`, or the next owner link; there is no config version/hash that self-re-pushes, so already-linked cars keep the old config until someone re-pushes.
> 2. **`0` and `null` must never be conflated on the wire.** A persisted `0` is emitted as the JSON number `0` (never omitted, never `null`); a never-read value is an explicit `null` (never a fabricated `0`). The `/snapshot` owner projection always carries both keys — same absent-vs-null discipline as the MYR-274/298 siblings. Persistence (MYR-273, migration 0010) is what carries the capability across a socket gap, so a sheet-open on a sleeping car still knows the seats are vented.

### 1.2 Design notes

- **`vehicleId` is the SDK identifier, not VIN.** Per FR-4.2, the SDK API is vehicle-scoped using the opaque database ID. VINs are internal to the telemetry server and never exposed to SDK consumers.
- **`speed` is NOT in the GPS group.** Although the requirements doc lists speed in the GPS group (NFR-3.1), the implementation broadcasts speed independently (high-frequency, 2s interval) while GPS/heading are delivered together. Speed is decoupled from GPS because it changes more frequently than position and does not require atomic consistency with coordinates. This is an intentional divergence documented here; the requirements doc should be updated to reflect this.
- **Integer rounding.** Tesla emits most numeric fields as floats. The telemetry server rounds `speed`, `heading`, `chargeLevel`, `estimatedRange`, `interiorTemp`, `exteriorTemp`, `odometerMiles`, and `etaMinutes` to the nearest integer before delivery. MYR-252 adds the cabin integer levels `fanSpeed`, `driverTempSetting`, `passengerTempSetting`, `seatHeaterLeft`/`seatHeaterRight`, `seatHeaterRearLeft`/`seatHeaterRearCenter`/`seatHeaterRearRight`, and `seatCoolerLeft`/`seatCoolerRight` to the same rounded-integer set (`internal/ws/field_mapping.go` `integerFields`). `mediaVolume` is deliberately excluded — it is a fractional level and stays a `number`. MYR-303 adds `mediaNowPlayingDurationMs` and `mediaNowPlayingElapsedMs` to the rounded-integer set (the contract types both as `integer`), and deliberately excludes `mediaVolumeMax` for the same reason as `mediaVolume`: it is the ceiling that value is divided by, so rounding it would make `mediaVolume / mediaVolumeMax` disagree with the car.
- **Coordinate order.** `navRouteCoordinates` uses `[longitude, latitude]` order (GeoJSON/Mapbox convention), NOT `[lat, lng]`.
- **`locationName` and `locationAddress` are derived fields.** They are reverse-geocoded from GPS coordinates on the server. They are NOT part of the GPS atomic group because they update asynchronously (geocoding is async) and are not sourced from Tesla telemetry.
- **`name` is sourced from the DB, not Tesla telemetry.** `VehicleState.name` comes exclusively from the DB `Vehicle.name` column (user-assigned via the Next.js settings UI). Tesla also streams a `VehicleName` proto field (decoded as internal field `vehicleName` in `internal/telemetry/fields.go`) at a 300s interval, but this value is received by the telemetry decoder and is NOT broadcast to SDK clients or used to populate the SDK `name` field. Rationale: (1) the user can rename their vehicle in the MyRoboTaxi app, so the DB is the source of truth for user-facing names; (2) Tesla's `VehicleName` may lag a user rename by up to 300s, creating stale-name confusion; (3) if Tesla-to-DB name sync is ever needed, that responsibility belongs to the Next.js app layer (which owns the `Vehicle` table via Prisma), not the telemetry server. The `Settings.teslaVehicleName` column (see `data-classification.md` §1.8) stores the Tesla-reported name separately and may differ from `Vehicle.name` if the user renames the vehicle in the MyRoboTaxi app.

## 2. Atomic group sub-schemas

### 2.1 Navigation group

**Requirement traceability:** FR-2.1, FR-2.2, FR-2.3, NFR-3.1, NFR-3.2, NFR-3.3, NFR-3.4

**Members:** `destinationName`, `destinationAddress`, `destinationLatitude`, `destinationLongitude`, `originLatitude`, `originLongitude`, `etaMinutes`, `tripDistanceRemaining`, `navRouteCoordinates`

**Server-side implementation:** The broadcaster routes all navigation-related Tesla fields (`DestinationName`, `DestinationLocation`, `OriginLocation`, `RouteLine`, `MinutesToArrival`, `MilesToArrival`) through the `groupAccumulator` (`internal/ws/group_accumulator.go`) registered against `groupNavigation` with a 500 ms flush window. When the first nav field arrives for a vehicle, a timer starts. All subsequent nav fields within the 500 ms window are merged into the batch. On timer expiry, the complete batch is broadcast as a single `vehicle_update` message. The 500 ms window aligns with Tesla's vehicle-side emission bucket floor; a shorter server window cannot improve atomicity because Tesla itself cannot deliver companion fields any faster (decision recorded by [MYR-14](https://linear.app/myrobotaxi/issue/MYR-14)).

**Nullability:** All navigation fields are nullable. When no navigation is active, all fields are `null`. This is the steady state for a parked vehicle or a vehicle driving without an active route.

**Nav cancellation:** When Tesla cancels navigation, it marks the nav fields as `Invalid`. The server atomically clears ALL navigation fields to `null` -- both in the WebSocket broadcast and in the database. This ensures the UI never displays a stale destination, ETA, or polyline (FR-2.3).

### 2.2 Charge group

**Requirement traceability:** FR-1.2, NFR-3.1

**Members (v1):** `chargeLevel`, `chargeState`, `estimatedRange`, `timeToFull`

**Server-side implementation:** All four fields are mapped from native Tesla Fleet Telemetry fields and delivered together in the same `vehicle_update` message when any of them change:

| Wire field | Tesla proto field | Notes |
|------------|-------------------|-------|

Tesla emits these fields on the shared 30-second charge cadence; all four are in `DefaultFieldConfig` as of [MYR-40](https://linear.app/myrobotaxi/issue/MYR-40) (2026-04-22). When any of the four change in the same Tesla 500 ms vehicle-side bucket they arrive in a single upstream `Payload` protobuf message and the broadcaster emits the four-field batch in one `vehicle_update`. If only a subset changes in the bucket, Tesla emits just that subset — atomic-group semantics are "siblings are included when they change together", not "every frame carries all four."

> **`chargeState` is the one charge-group member that LATCHES — it carries a resend ([MYR-333](https://linear.app/myrobotaxi/issue/MYR-333)).** Tesla emits proto 179 **on change only**, and for a charging session the change fires exactly once: at plug-in. A server that was not subscribed at that instant — a reconnect, a deploy, a car plugged in while asleep, or a fleet-config pushed after the session began — never hears `Charging` again for the whole session, and `chargeState` sits at its last value (commonly `Disconnected`, or `null` on a car that has never charged) until the session ENDS and the next transition fires. This is the same failure class as MYR-300 (`HvacPower`) and MYR-299 (the seat coolers), and it is the client-reported defect of MYR-333: a car being charged at a service centre showed no charging state, while the SAME screenshot showed the Charge tile reading "Port open" — because its proto 183 sibling `ChargePortDoorOpen` has carried a 120s resend since MYR-252 and re-asserts itself — and the battery climbed 74% → 76% in the same window, proving the data path was healthy and only this field was latched. `FleetFieldDetailedChargeState` therefore carries `ResendIntervalSeconds: 120`, matching the comfort/media family and the `defaultStreamFreshness` window the MYR-300 backfill gate is sized against (so a genuinely-streaming car re-emits `chargeState` at least once per window, which is what makes dropping the REST copy of it safe). **The three siblings deliberately carry NO resend**: `chargeLevel`, `estimatedRange` and `timeToFull` all move continuously while charging, so on-change emission refreshes them by itself. **Propagation:** a `DefaultFieldConfig` change reaches a car only on a **re-push** — `POST /api/fleet-config/{vin}`, `ops fleet-config push`, or the next owner link; there is no config version/hash that self-re-pushes, so already-linked cars keep the old config until someone re-pushes.

**No server-side accumulator** is registered for `groupCharge` (decision recorded by [MYR-14](https://linear.app/myrobotaxi/issue/MYR-14)). Tesla's 500 ms vehicle-side bucket is the atomicity guarantee; layering a server-side debounce on top would delay charge updates by the flush interval with zero benefit since the upstream cannot deliver companions faster. The `groupAccumulator` is generalized over groupID so a future MYR can opt charge in if empirical capture ever shows the bucket guarantee fails.

**Nullability:** `chargeLevel` and `estimatedRange` are non-nullable and default to `0` in the database on vehicle creation. A value of `0` for `chargeLevel` with `status: offline` means "unknown"; with `status: driving` it means "critical". `chargeState` and `timeToFull` are nullable in steady state — the Prisma-owned `Vehicle` columns are `String?` / `Float?` (post-MYR-41) and a vehicle that has never charged (or whose first charge frame has not arrived yet) surfaces `null` on both wire and REST snapshot. SDK consumers MUST tolerate `null` for these two fields and render a neutral placeholder rather than a spinner.

**Implementation status:** live WS wiring completed by [MYR-40](https://linear.app/myrobotaxi/issue/MYR-40) — `FleetFieldChargeState` (proto 2) and `FleetFieldTimeToFullCharge` (proto 43) added to `DefaultFieldConfig`; both are in `fieldMap`; `convertChargeState` routes the proto 179 `Value_DetailedChargeStateValue` enum (with proto 2 `Value_ChargingValue` fallback) via `chargingStateString`; `timeToFull` passes through `convertNumericOrString` as `float64` hours. DB persistence completed by [MYR-41](https://linear.app/myrobotaxi/issue/MYR-41) on 2026-04-25 — Prisma migration adds `chargeState String?` + `timeToFull Float?` to `Vehicle`, the Go writer pipeline applies both fields from `VehicleTelemetryEvent.Fields` on every event, and `internal/store` SELECT/UPDATE round-trips them to the cold-load snapshot path.

### 2.3 GPS group

**Requirement traceability:** FR-1.1, NFR-3.1

**Members:** `latitude`, `longitude`, `heading`

**Server-side implementation:** `Location` (a compound `{latitude, longitude}` value from Tesla) is split into separate `latitude` and `longitude` fields for the client. `GpsHeading` is delivered alongside. Tesla emits `Location` with a 10-meter minimum delta filter to suppress GPS jitter while parked.

**No server-side accumulator** is registered for `groupGPS` (decision recorded by [MYR-14](https://linear.app/myrobotaxi/issue/MYR-14)). Atomicity of `latitude`/`longitude` is upstream-guaranteed: both values arrive in the same Tesla `Location` protobuf field, so they are split server-side and never broadcast independently. `heading` flows independently — both DB columns are non-nullable with default `0`, so the §3.3 "heading accompanies coordinates" predicate is satisfied at write time without a debounce layer.

**Nullability:** Non-nullable in the database (default `0`). A position of `(0, 0)` indicates no GPS fix has been received. SDK consumers SHOULD treat `latitude == 0 && longitude == 0` as "no position available" rather than a valid location in the Gulf of Guinea.

### 2.4 Gear group

**Requirement traceability:** NFR-3.1

**Members:** `gearPosition`, `status`

**Server-side implementation:** When a `Gear` telemetry event arrives, the server maps it to `gearPosition` and derives `status` using `deriveVehicleStatus()`: gear D or R = `driving`, otherwise = `parked` (or `in_service` — see below). Both fields are included in the same `vehicle_update` message.

**No server-side accumulator** is registered for `groupGear` (decision recorded by [MYR-14](https://linear.app/myrobotaxi/issue/MYR-14)). `status` is derived synchronously from `gearPosition` at broadcast time, so the two fields are produced in the same code path within the same frame — there is no temporal split for an accumulator to reconcile.

**Speed-only frames recompute `status` against the cached gear ([MYR-61](https://linear.app/myrobotaxi/issue/MYR-61)).** The broadcaster keeps a per-VIN cache of the most recently seen `gearPosition`. On a frame carrying only `speed`, the cached gear is injected into the wire payload and `status` is derived from the combined fields, so the gear group remains atomic on the wire (`status` never appears without `gearPosition`). Implemented in [`internal/ws/nav_broadcast.go`](../../internal/ws/nav_broadcast.go) `ensureGearGroupAtomic`. The cache is wiped on connectivity disconnect to prevent stale gear from leaking across reconnects. Cold-start frames (no cache hit yet) leave `status` off the wire so the SDK keeps its prior value rather than receiving a partial group.

**Persisted `status` follows the stream ([MYR-454](https://linear.app/myrobotaxi/issue/MYR-454)).** Everything above describes the **live wire**. Until MYR-454 none of it reached the **persisted** `Vehicle.status` column, and that split was a user-visible bug: an external-beta tester driving a healthy, streaming car saw "Parked" on the map sheet, twice, an hour apart, while Tesla's own app showed driving. The column had exactly two writers — `drive.ended` → `parked` and the `ServiceStatusMonitor` → `in_service`/`parked` — and **neither ever wrote `driving`**; `drive.started` wrote no status at all. Every DB-backed surface (REST `/snapshot`, the WS on-connect snapshot, `GET /api/vehicles` behind the map sheet) therefore served the value the *previous* drive's end had latched, for the entire duration of the current drive. Prod rows contradicted themselves outright: `status='offline'` beside `speed=21` and `gearPosition='D'`, written by the same flush.

The fix makes the column a **function of the row's own motion columns**, folded into the *same* `UPDATE` that writes them (`appendDerivedStatusSet`, [`internal/store/vehicle_update_builder.go`](../../internal/store/vehicle_update_builder.go)) — so it is atomic with the gear/speed write and there is no window in which **the row** can disagree with itself. The arms, in order:

1. **`in_service` is preserved above the motion arms** — deliberately the *opposite* of `deriveVehicleStatus()`. See "Why the persisted precedence differs" below.
2. gear `D`/`R`, **or** `speed > 0` → `driving`
3. `charging` is **preserved** when stationary — no Go path writes it, and the Prisma-owned table is shared with the Next.js app, which does
4. else → `parked`, **including from `offline`**. A live frame arriving is proof the car is not offline, so ingest heals the `NOT NULL DEFAULT 'offline'` that owned-vehicle provisioning never overwrites.

A frame carrying **no** motion column (climate-only, media-only) does not re-derive at all. Because bare column references on the right-hand side of a `SET` read the *old* row, a **speed-only** frame resolves against the last gear stored — which is what makes this work at all, since Tesla emits `Gear` **on change only** and a car that shifted into `D` once sends nothing but speed for the rest of the drive. Status tracks the stream within one flush interval (5s).

**The old row is only trusted while it is fresh.** `Gear` and `VehicleSpeed` carry no `ResendIntervalSeconds`, so a gear change made while the socket was down is lost forever — a car that drops connection at 45 mph in `D` keeps `gearPosition='D'`, `speed=45` indefinitely, and a lone `speed=0` frame on reconnect would resolve against that stale `D` and latch `driving` onto a parked car ([MYR-393](https://linear.app/myrobotaxi/issue/MYR-393), the inverse bug). The broadcaster already wipes its own gear cache on disconnect for this reason; the column has no such wipe, so the fallback is bounded against the row's previous `lastUpdated` (**5 minutes**). A car genuinely still moving says so with `speed > 0` on its very next frame.

**Only STREAMED frames fold.** MYR-260's synthetic `/vehicle_data` frames are published precisely when the monitor has determined the car is **not** streaming, and they carry Tesla's *cached* `speed` and `shift_state`. Folding on one would heal `offline` using evidence that the car is asleep. Provenance is carried into the store on `VehicleUpdate.Streamed`.

**Why the persisted precedence differs from the wire.** On the live wire `driving` outranks `in_service` (§2.4 rule 1), and that is safe there because the broadcaster keeps an independent cached `ServiceMode` bool, so the value returns by itself when the car stops. The **column has no such fallback**, and losing `in_service` in it is a **one-way door**: the MYR-320 periodic re-poll selects `WHERE "status" = 'in_service'` (`queryInServiceVINs`), so a car folded out of `in_service` drops off the very worklist meant to restore it. A tech moving a car across the service lot would silently disarm the MYR-372 dispatch hold and the accept-path `409`, sending a rider to meet a car on a lift. Showing `in_service` for a car being test-driven is the safe way to be wrong, so the persisted arm preserves it.

**This is not the only writer of the column,** and any change here must account for the others: `drive.ended` writes `parked` as a backstop; `ServiceStatusMonitor` writes `in_service` unconditionally and its `parked` **connected baseline** through a guarded write (`UpdateStatusBaseline`) that applies only over `in_service`/`offline`, so a connectivity edge cannot stomp a `driving` the fold just derived; and the partner Next.js app writes the same Prisma-owned column with a precedence of its own. The fold is the authority for the `driving`/`parked` distinction only.

**In-service derivation ([MYR-259](https://linear.app/myrobotaxi/issue/MYR-259)).** `status` is `in_service` when **either** in-service signal is set: the pushed **`ServiceMode`** telemetry field (Tesla proto **159**, `bool`) **OR** Tesla's authoritative REST `in_service` bool. `deriveVehicleStatus()` is the single place that encodes the precedence for the live wire status:

1. **`driving` always wins** — gear `D`/`R` (or `speed > 0`) yields `driving` even while a signal reports in-service. A service tech test-driving a car must surface as `driving`, not `in_service`.
2. **`in_service` outranks `parked`** (and `charging`/`offline`) — a car a tech has put into service mode is not "just parked".
3. Otherwise `parked`.

`ServiceMode` is an **internal-only** signal: it is decoded ([`internal/telemetry/fields.go`](../../internal/telemetry/fields.go), `convertBool`), cached per-VIN by the broadcaster, folded into the in-service derivation, and then **stripped** before broadcast — it never appears as its own wire field (only the derived `status` is emitted). It is added to `DefaultFieldConfig` at a 60s interval + 300s resend (it changes rarely). A bare `ServiceMode` toggle recomputes `status` against the cached gear so an in-service flip surfaces live even on an otherwise-static parked car; the cache is wiped on connectivity disconnect alongside gear.

The **REST `in_service` bool** is read edge-triggered (NOT polled): the [`ServiceStatusMonitor`](../../internal/telemetry/service_status_monitor.go) subscribes to `ConnectivityEvent` and, on each connect/disconnect edge, fires **one** debounced (per-VIN, ~45s cooldown) authoritative `GET /api/1/vehicles/{vin}` read and persists the **resolved** status to `Vehicle.status`. Read failures are non-fatal (last-known preserved). This is the first code path to emit/persist the `in_service` enum value, which has always been part of the `status` enum (additive-safe — no consumer change).

**Owner-control backfill for non-streaming cars ([MYR-260](https://linear.app/myrobotaxi/issue/MYR-260)).** The same edge read is extended so that when it shows the car is **not streaming to us** (`in_service:true`, or connectivity `state != "online"`) the monitor also issues **one** `GET /api/1/vehicles/{vin}/vehicle_data` read and republishes the stream-only owner-control fields (Lock / Trunk / Climate / Charge / Odometer / Temps) through the normal broadcast/persist path. It reuses the same ~45s per-VIN debounce (so at most one `/vehicle_data` call per cooldown) and is strictly **non-waking** — an asleep/offline `408` is a silent skip. Streaming cars (online, not in service) are never read this way, since their live stream already carries honest values. See the MYR-260 note under §1.1 *Cabin control fields* for the field-by-field mapping.

**Stream-recency gate on the backfill ([MYR-300](https://linear.app/myrobotaxi/issue/MYR-300)).** Tesla's connectivity flag **lags reality** — a car that is actively streaming to us can still read `asleep`/`offline` on the edge read for minutes — so `notStreaming()` alone is not a sufficient guard, and the backfill *does* fire for streaming cars. Because `/vehicle_data` can answer from a **stale cache** and the synthetic frame carries `CreatedAt = now`, a non-nil stale value wins the per-field COALESCE control-state upsert and **durably overwrites fresher streamed state**. Client-verified symptom: the car's own screen read "Cooling Down 69" while the app read "Climate off". The monitor therefore keeps a **per-VIN last-live-frame timestamp**, stamped from the `TopicVehicleTelemetry` subscription it already holds (no new bookkeeping layer), and applies this rule:

> **Freshness rule.** If a **live** streamed frame has arrived for this VIN within the freshness window, the stream is authoritative and current: the backfill drops **every stream-sourceable field** from its frame before publishing. The window is `defaultStreamFreshness` = **120s**, sized to the `HvacPower` `ResendIntervalSeconds` — a genuinely streaming car re-emits its control state at least that often. The boundary is **exclusive**: an age of exactly 120s counts as stale.

Three properties make the rule safe:

- **It covers all control fields, not just `hvacPower`.** The dropped set is derived from the decoder's `fieldMap` (`internal/telemetry/fields.go`), so `locked`, `frunkOpen`/`trunkOpen` (via `doorState`), `isClimateOn`, `chargePortDoorOpen`, the temps, `chargeState`, `chargeLevel`, `odometerMiles` and `softwareVersion` are all gated — the same stale-cache overwrite can hit any of them — and a future streamed field is covered automatically.
- **REST-only fields still flow.** `trim` (MYR-279) is not in `fieldMap`: Tesla never streams the trim badge, so REST is its only source and it can never be a stale overwrite. Gating it would mean a busily-streaming car could never acquire it.
- **Non-streaming cars are untouched.** A car that is asleep, offline, or in service has no fresh stamp, so the full MYR-260 backfill applies exactly as before — which is the whole point of the non-waking read. The backfill's own synthetic frame is tagged `events.SourceRESTBackfill` so it never counts as "streamed" (otherwise the gate would latch on its own output and suppress every subsequent backfill for a sleeping car), and a **disconnect** edge clears the stamp immediately so the backfill that edge exists to trigger is not suppressed while the window lapses.

Companion fix in the same issue: `HvacPower` gains `ResendIntervalSeconds: 120` in `DefaultFieldConfig` (it previously had none, unlike its sibling comfort fields). Tesla emits it **on change only**, so a server that reconnected while the car was already cooling could never re-learn HVAC power. **Propagation:** a `DefaultFieldConfig` change reaches a car only when the config is **re-pushed** — `POST /api/fleet-config/{vin}`, `ops fleet-config push`, or the next owner link. There is no config version/hash that triggers a self-re-push, so **already-linked cars keep the old config until someone re-pushes**; the stream-recency gate is what protects them in the meantime.

**Persisted transition IN and OUT of `in_service`.** The persisted `Vehicle.status` column (read by `GET /api/vehicles` and the on-connect snapshot) needs both directions — the wire-only live derivation is not persisted, so the DB column would otherwise only ever leave `in_service` via a completed drive, stranding a car that comes back from service and parks without driving at "In Service" forever. The `ServiceStatusMonitor` owns both:

- **IN:** a `ServiceMode` OFF→ON telemetry edge, or a connectivity-edge REST read returning `in_service:true`, persists `in_service`.
- **OUT (reconnect / any connectivity edge):** when the REST read returns `in_service:false` and `ServiceMode` is not on, the resolved write persists **`parked`** — the neutral connected baseline (the live stream refines to `driving`/`charging` as frames arrive). This clears a stale `in_service` on the next edge after leaving service.
- **OUT (continuously-connected, no disconnect):** a `ServiceMode` ON→OFF telemetry edge triggers an authoritative reconcile that persists `parked` **unless** the REST read independently still reports `in_service:true` (the `OR` still holds). On a read failure here the live `ServiceMode`-off signal is trusted → `parked`, so the car never stays stuck.

A genuinely in-service car (`ServiceMode` on OR REST `in_service` true) is never flapped out while a signal holds. Writes are debounced per-VIN; every failure mode is non-fatal. Persisting `parked` as the connected baseline is the neutral value for a car that is not in service; the telemetry fold below immediately refines it to `driving` if the car is in fact moving.

> **UPDATED by [MYR-454](https://linear.app/myrobotaxi/issue/MYR-454).** This paragraph used to read "the persisted column is coarse — it holds `offline` (default) / `parked` / `in_service`; `driving` and `charging` are live-derivation-only". That coarseness was not a design choice, it was the bug: it meant every DB-backed surface said **Parked for the entire duration of a real drive**. The column now also holds `driving`, written by the telemetry fold (§2.4 "Persisted status follows the stream"). `charging` remains unwritten by this server.

**The service window — `serviceEstimatedEndAt` ([MYR-316](https://linear.app/myrobotaxi/issue/MYR-316)).** `in_service` says the car is in the shop; it cannot say *when it comes back*, which is the only part of the answer a user can act on — and it is what the rider's scheduling picker needs as a FLOOR. That is `serviceEstimatedEndAt`, and it belongs to this section because it lives and dies with the `in_service` derivation above.

**Two columns, one emitted value.** Migration **0017** adds `service_etc` and `service_expected_end_at` (both nullable `TIMESTAMPTZ`) to the Go-owned `go_vehicle_control_state` side table, and the wire value is `COALESCE(service_etc, service_expected_end_at)` — **Tesla's own estimate outranks the owner's**, resolved by one shared helper ([`internal/telemetry/service_window.go`](../../internal/telemetry/service_window.go)) that the `/snapshot`, the vehicles list, and the §7.8 scheduler bound all call, so the three readers cannot drift. The split is deliberate: one merged column would let a late Tesla estimate ERASE what the owner typed, and would make a WITHDRAWN Tesla estimate fall back to `null` rather than back to the owner's answer. Both columns also bypass the shared per-field COALESCE control-state upsert — that upsert cannot express a NULL write, and clearing is first-class here — so they have dedicated writers in `internal/store/vehicle_service_window.go`.

- **Tesla half.** `service_data.service_etc`, read from the Fleet API `GET /api/1/vehicles/{vin}/service_data` on the SAME `ServiceStatusMonitor` connectivity-edge path described above, for an `in_service` vehicle only. It shares the SAME per-VIN read debounce (`defaultServiceReadCooldown`, ~45s) as the `GET /api/1/vehicles/{vin}` edge read and the MYR-260 `/vehicle_data` backfill, and reuses the token that read already resolved — one more read on a path that was already firing, not a new poller. Failures are non-fatal and leave the last-known estimate. **Every field of that response is nullable, and an ALL-NULL body is COMMON AND NORMAL** — it is what a visit with no appointment record looks like.
- **Owner half.** `service_expected_end_at`, written only by the owner via `PUT /api/tesla/vehicles/{vehicleId}/service-window` (rest-api.md §7.16), which requires a FUTURE instant and accepts four equivalent spellings of a clear.

**Gated on `in_service`, and cleared on the way out.** The field is emitted only while the vehicle's `status` is `in_service`; every other status reads `null`. The monitor ALSO physically clears both columns when it observes the car leaving service — the same OUT transitions enumerated above — so the in-service gate is belt-and-braces: a stale window can neither outlive the visit nor be resurrected by a status flip, and consumers never need to age the value out themselves. The practical consequence is that an owner may have to re-enter the value for a subsequent visit; that is intended.

**`null` means NO BOUND, never "unknown, refuse".** Because an absent estimate is the normal shape rather than a failure, a null value must never narrow what anyone may do: the scheduling picker stays fully open, and the server's own `scheduledFor` bound (rest-api.md §7.8, `400 invalid_request`) simply does not apply. Where the value IS present, the bound is strictly "earlier than" — a `scheduledFor` exactly equal to `serviceEstimatedEndAt` is allowed.

**Not streamed.** Tesla has no proto for a service ETC, so there is no `fieldMap` entry, no fleet-config change, and no `vehicle_update` frame ever carries `serviceEstimatedEndAt` — the same REST-only shape as `trim` (MYR-279) and `seatCoolingCapable` (MYR-308), and for the same reason it is untouched by the MYR-300 stream-recency gate. It reaches clients on the next `/snapshot` or vehicles-list read.

**Nullability:** `gearPosition` is nullable (`null` = vehicle asleep or gear not yet reported). `status` is non-nullable (default `offline`). `serviceEstimatedEndAt` is nullable and is `null` for every vehicle that is not `in_service`.

### 2.5 Setup state — `setupState` ([MYR-491](https://linear.app/myrobotaxi/issue/MYR-491))

`status` can say a car is `offline`. It cannot say **why**, and for one population that distinction is the whole product: a car that has been linked but has never streamed sits at `offline` **permanently**, because the column is `NOT NULL DEFAULT 'offline'` and nothing writes it until the first mTLS stream event ([MYR-437](https://linear.app/myrobotaxi/issue/MYR-437)). Every new owner is in that population for their first minutes or days. `setupState` is the field that explains it, which is why it belongs in this section beside the `status` derivation it qualifies.

**The states, and the action each implies.**

| `state` | Means | Who acts |
|---|---|---|
| `awaiting_owner_acknowledgment` | This car was linked by somebody Tesla reports as a **DRIVER** of it rather than its owner, and nothing has been pushed at it — no fleet-telemetry config, no re-push, nothing. `since` is when the driver-access row was recorded. | **The linker** — confirm the owner approved adding this car (`POST /api/tesla/vehicles/{vehicleId}/acknowledge-owner-approval`, rest-api.md §7.29). |
| `owner_access_required` | Tesla **REFUSED** to create this car's telemetry config, because the linking account holds DRIVER access and Tesla's Fleet API lets only the vehicle's OWNER account create one. `since` is when the refusal was observed. | **Not the linker, and NOT by reconnecting.** The car's Tesla **owner** must add it in MyRoboTaxi under their own account and share it with the driver. |
| `awaiting_virtual_key` | Tesla refused to apply the telemetry config because the owner's virtual key is not enrolled on the car (Tesla's own `missing_key` / `not_paired` skip reason). Every signed command will also be rejected. | **The owner** — pair the key in the Tesla app. Nothing the server does heals this. |
| `configuring` | The configuration side is in hand and the server is waiting for the car to open its telemetry session, including after a MYR-489 forced re-push. | **Nobody.** Copy should say so; past a few minutes it may suggest waking the car's screen. |
| `token_failed` | The owner's Tesla authorization can no longer be resolved or refreshed, so neither config pushes nor commands can reach the car. | **The owner** — reconnect the Tesla account. |
| `null` | **No claim.** | — |

**The order of that table is the PRECEDENCE, and it is contractual** ([MYR-599](https://linear.app/myrobotaxi/issue/MYR-599)). `awaiting_owner_acknowledgment` is evaluated **before every other arm, including the "no schedule row ⇒ no claim" short-circuit**, for three independently sufficient reasons: it is the only state read out of a row that exists from the instant the car was provisioned, so a failed best-effort seed cannot blind it; **nothing has been pushed** at such a car, and the other four are all claims ABOUT a push; and consent precedes pairing evidence, so any other arm would name the wrong next action. `owner_access_required` sorts immediately after it — the only state it can follow, since the refusal is observable only on a push and no push happens before consent is on record — and before the remaining three, because a definitive refusal is not progress and "waiting for the car" would be fabricated.

**`owner_access_required` is emitted only on POSITIVE EVIDENCE, and the reason is that Tesla's refusal is not self-describing.** The config POST answers a generic `404 {"error": "<VIN> not_found"}` for a driver token while **that same token still lists the car** — and a revoked grant answers the identical 404. So the server names the driver cause only when a `go_vehicle_driver_access` row exists for the car (acknowledged, necessarily: nothing pushes at a car whose gate is shut), and reports `token_failed` for a bare 404, whose copy — reconnect your Tesla account — is right for the revoked grant that a bare 404 overwhelmingly is. The third condition contracts v0.40.0 names, the VIN still appearing in the same token's vehicle list, is established at LINK time: that listing is the only moment this server enumerates a fleet, and it is what created the row being read. It is deliberately not re-verified per push.

**And it may stop being true without any change here.** Tesla staff called DRIVER-token config creation "coming soon" on `teslamotors/fleet-telemetry` [#116](https://github.com/teslamotors/fleet-telemetry/issues/116) and [#126](https://github.com/teslamotors/fleet-telemetry/issues/126) (2024-03-14), and as of 2026-09-05 no announcement says it shipped. If it does, the next push simply succeeds, this state stops being produced, and no consumer changes. `teslaAccessType` stays `"driver"` either way — it is a fact about the car, not about its setup.

**Derived once, server-side, from state that already exists.** The inputs are the Go-owned `go_fleet_config_attempts` row — `last_outcome`, `last_attempt_at`, `signed_command_at`, `forced_repush_at` (migrations 0031 and 0036) — read together with the Go-owned `go_vehicle_driver_access` row (migration 0046) and the vehicle row's own `status` and `lastUpdated`. One function serves both `VehicleState.setupState` and `VehicleSummary.setupState`, so the detail sheet and the catalog row cannot disagree for a vehicle, and **no client re-derives it**. The link-time config push seeds `awaiting_virtual_key` the moment Tesla answers `missing_key`, so the state exists within seconds of onboarding rather than after the reconciler's first pass.

**Four honesty rules, and they are part of the contract.** Each exists because the alternative is a card telling a customer something false:

1. **Absence of evidence yields `null`.** A vehicle with no schedule row never carries a state. The table is self-draining — a successful config push DELETEs the row — so a healed car loses its card the same moment it stops needing one. **Nor does mere PRESENCE license a card** (MYR-517): a row may be a SEED written at link time or by an applied signed command, carrying `last_outcome = ''`, and an empty outcome yields `null` exactly as no row does. Only a row whose outcome names something observed can produce a state.
2. **`configuring` expires** 24 hours after the evidence behind it, falling back to `null` — **never to `awaiting_virtual_key`**. A car whose pairing has been PROVEN is not awaiting a key, and telling its owner to re-pair would send them to fix something that is not broken. Nothing here says "connecting…" forever.
3. **A car that is currently streaming never carries `configuring` or `token_failed`.** Nothing deletes a schedule row when a car heals itself, so a stale row could otherwise put a setup card on a live vehicle.
4. **A car that streamed once and later went quiet is the freshness story, not a setup state.** That case belongs to `lastUpdated` and its own UI. `setupState` is about cars that have never come up, not cars that have gone away.

**`null` is not `ready`.** There is deliberately no `ready` member: `null` also covers a car nobody has examined and an expired claim, and it is what a pre-MYR-491 server produces by omitting the key. A consumer must not paint a positive "set up ✓" badge from a value that means "no claim".

**Not derived from `key_not_paired` command rejections.** That was the obvious second source and it is deliberately excluded: the error code is overloaded — the server returns the very same `key_not_paired` when ITS OWN signing proxy is unconfigured — so it cannot distinguish an unpaired owner from a broken deployment, and a card built on it would tell the entire fleet to re-pair whenever our proxy config broke. Tesla's `missing_key` on the config push carries no such ambiguity.

**Not streamed.** No proto, no `fieldMap` entry, no `vehicle_update` frame — the same REST-only shape as `serviceEstimatedEndAt` (MYR-316) and `seatCoolingCapable` (MYR-308), and untouched by the MYR-300 stream-recency gate for the same reason. It reaches clients on the next `/snapshot` or vehicles-list read, which is sufficient: its inputs change on reconciler passes and owner actions, not on telemetry frames, and a car in any of these states is by definition not sending frames to attach an update to.

**Nullability:** `setupState` is nullable and is `null` for the overwhelming majority of vehicles. When non-null, both members are always present.

## 3. Atomic-group consistency predicates (NFR-3.3)

These predicates define what constitutes a valid vehicle state snapshot. The server MUST enforce these on every DB write. The SDK validates these on snapshot load and live updates.

> **Enforcement boundary.** The predicates in this section are **semantic invariants** -- they constrain _values_ (null vs non-null, cross-field equivalence, enum derivation) in ways that JSON Schema cannot express. JSON Schema keywords like `dependentRequired` only enforce the _presence_ of sibling _keys_, not the non-nullness of their values, and `dependentSchemas` cannot express "if A's value is non-null, then B's value must be non-null" across independently-typed fields. Therefore these predicates are **NOT enforced by the `vehicle-state.schema.json` file** -- they are enforced at runtime by the [`contract-tester`](../../.claude/agents/contract-tester.md) agent's FR/NFR conformance suite, and at write-time by the server's persistence layer. Any wording below that sounds prescriptive applies to the runtime validators, not the schema. If you need to confirm an invariant, check the `contract-tester` fixtures, not `vehicle-state.schema.json`.

### 3.1 Navigation group predicates

Enforced by `contract-tester` (runtime) + server persistence layer (write-time). NOT enforced by JSON Schema.

1. **Coordinate pairs are atomic.** If `destinationLatitude` is non-null, then `destinationLongitude` MUST also be non-null, and vice versa. Same rule applies to `originLatitude`/`originLongitude`. (`dependentRequired` in the schema enforces _key presence_ as a weaker best-effort hint, but the non-null invariant is a semantic check by `contract-tester`.)

2. **Active navigation completeness.** If `destinationName` is non-null, then `destinationLatitude`, `destinationLongitude`, and `navRouteCoordinates` MUST also be non-null (NFR-3.3). The reverse is also true: if `navRouteCoordinates` is non-null, then `destinationName` MUST be non-null. Semantic invariant only; not schema-enforceable.

3. **All-or-nothing clear.** When navigation is cancelled, ALL navigation fields MUST be null. A snapshot where `destinationName` is null but `navRouteCoordinates` is non-null is invalid (FR-2.3, NFR-3.4). Semantic invariant only; not schema-enforceable. The prior `x-spec-only` exemption was retired by MYR-24 (2026-04-23) — no field in the navigation group is currently exempt.

4. **ETA/distance independence during accumulation.** `etaMinutes` and `tripDistanceRemaining` MAY arrive slightly after other nav fields during the 500ms accumulation window. However, the DB snapshot (used for cold page load) MUST be fully consistent -- these fields are either all present or all null. Semantic invariant only; not schema-enforceable.

### 3.2 Charge group predicates

1. **Both fields present.** `chargeLevel` and `estimatedRange` are always present in the DB snapshot (non-nullable, default 0). There is no partial charge state.

### 3.3 GPS group predicates

1. **Coordinate pair atomic.** `latitude` and `longitude` MUST always be updated together. A state where one is non-zero and the other is zero is invalid (except for the edge case of `latitude == 0` at the equator, which is handled by the GPS delta filter).

2. **Heading accompanies coordinates.** `heading` MUST be present whenever `latitude`/`longitude` are present (both are non-nullable with defaults).

### 3.4 Gear group predicates

1. **Gear-to-status derivation.** When `gearPosition` is `D` or `R`, `status` MUST be `driving` — this outranks every other state, including `in_service` (a tech test-driving surfaces as `driving`). When `gearPosition` is `P` or `N`, `status` MUST be `parked` unless overridden by `charging`, `offline`, or `in_service`. `in_service` (from `ServiceMode` proto 159 OR Tesla's REST `in_service` bool) outranks `parked`/`charging`/`offline` but is itself outranked by `driving` (MYR-259, §2.4).

2. **Status is never null.** Even when `gearPosition` is null, `status` has a valid value (typically `offline`).

## 5. JSON Schema file

The canonical JSON Schema (draft-2020-12) is committed at:

```
docs/contracts/schemas/vehicle-state.schema.json
```

This file is the single source of truth for the `VehicleState` shape. Type generators, contract tests, and SDK implementations all derive from this file.

### 5.1 Extension keywords

The schema uses the following `x-*` extension keywords for tooling and contract enforcement:

| Keyword | Purpose | Example |
|---------|---------|---------|
| `x-classification` | Data classification tier from `data-classification.md` | `"P0"`, `"P1"` |
| `x-encrypted` | Whether the field requires AES-256-GCM encryption at rest | `true` |
| `x-atomic-group` | Atomic group membership (per field) | `"navigation"`, `"charge"`, `"gps"`, `"gear"` |
| `x-unit` | Physical unit for numeric fields | `"mph"`, `"miles"`, `"degrees"`, `"percent"`, `"fahrenheit"`, `"minutes"` |
| `x-atomic-groups` | Root-level object defining all atomic groups, members, and predicates | See schema file |

### 5.2 Sub-schemas (`$defs`)

The schema deliberately contains **no `$defs`**. Atomic group membership is encoded entirely via per-field `x-atomic-group` annotations and the root-level `x-atomic-groups` object (which lists each group's fields, consistency predicates, and nullability rules). Earlier drafts defined `NavigationGroup`/`ChargeGroup`/`GpsGroup`/`GearGroup`/`Coordinate` sub-schemas under `$defs`, but none of them were ever `$ref`'d from the main schema -- they were dead code -- and atomic-group validation happens at runtime in `contract-tester` (see §3), not through schema composition. To avoid confusing type generators and contract tooling with unreachable definitions, those stubs were removed.

### 6.3 DoorState decode (`frunkOpen` / `trunkOpen`) — MYR-252

Tesla proto field 58 (`DoorState`) is NOT a scalar. It is emitted via the `Doors` protobuf message (the `door_value` oneof variant, tag 21) — a struct of six booleans:

```
message Doors {
  bool DriverFront    = 1;
  bool DriverRear     = 2;
  bool PassengerFront = 3;
  bool PassengerRear  = 4;
  bool TrunkFront     = 5;  // the frunk
  bool TrunkRear      = 6;  // the rear trunk
}
```

The telemetry decoder (`internal/telemetry/converters_doors.go`) folds the six booleans into an `int64` **bitmask** carried as the internal `doorState` field, using the shared bit layout in `internal/events/door_bits.go` (bit 0 = DriverFront … bit 4 = frunk = `TrunkFront`, bit 5 = trunk = `TrunkRear`). The WebSocket layer (`internal/ws/door_fields.go`) then unpacks the two bits the contract surfaces — `frunkOpen` (bit 4) and `trunkOpen` (bit 5) — and does NOT emit the raw `doorState` int on the wire. The other four door bits are decoded but intentionally not contracted (the owner controls only read back frunk/trunk). Defining the bit layout in `internal/events` (imported by both the pack and unpack ends) prevents the two sides from drifting.
